## Context

카드 번호를 토큰으로 바꿔 결제하는 TSP 시스템에는 카드 키를 다루는 키 관리 시스템(KMS)이 필요하다.
키 원재료는 HSM(하드웨어 보안 모듈) 밖 — DB, 로그, API 응답 어디에도 — 평문으로 나와서는 안 된다.
실장비(AWS CloudHSM)를 붙이기 전, PKCS#11 연동과 업무 흐름을 검증하는 PoC부터 시작했다.

## Problem

키는 잃어버리면 끝이라 백업이 필수다. 백업 파일은 KEK(키 암호화 키)로 감싸서 내보낸다.
그런데 초기 구조에서는 **백업 파일이 어떤 KEK로 감쌌는지에 대한 보장이 없었다.**
KEK가 여러 세대로 교체되는 환경에서, 복원 시점에 다른 세대의 키를 집으면
복원은 "성공"한 것처럼 보이지만 내용물은 쓰레기가 된다. 카드 키라면 사고다.

경계 조건도 얽혀 있었다. 시스템이 처음 켜진 것인지 KEK가 유실된 것인지 구분할 근거,
같은 세대 번호가 충돌 없이 조용히 흡수되는 문제까지 —
"복원이 된다"와 "옳은 키로 복원된다"는 전혀 다른 문제였다.

## Approach

세 가지를 연결해 잘못된 키 사용을 구조적으로 차단했다.

1. **키 주소 체계 통일** — 인프라 키의 식별자(CKA_ID)를 전용 대역으로 통일하고,
   세대 번호가 충돌하면 조용히 넘어가지 않고 기동 시점에 멈추게 했다.
2. **백업에 지문 기록** — 백업 파일에 그 파일을 감싼 KEK의 지문(KCV, Key Check Value)을 함께 기록했다.
3. **기동·복원 시 지문 대조** — 복원할 때 현재 KEK의 지문과 파일에 기록된 지문을 대조해,
   다르면 복원을 거부한다. 시스템 기동 시에도 같은 대조를 거쳐 "최초 기동"과 "KEK 유실"을
   백업 기록이라는 증거로 구분한다.

실장비 없이 개발해야 하는 제약은 추상화로 풀었다. Mock, 소프트웨어 에뮬레이터, CloudHSM 실장비가
**같은 계약(contract)을 구현**하고, 같은 계약 테스트를 통과하게 만들었다.
Mock은 실장비가 거부하는 동작을 똑같이 거부한다. 실장비 전환은 라이브러리 경로 교체로 끝난다.

<Callout label="원칙">키 원재료 평문은 로그·응답·감사 기록·예외 메시지 어디에도 남기지 않는다. 디버깅 편의로 뚫어둔 우회 API는 기능 플래그로 끄는 게 아니라 코드째 제거했다.</Callout>

## Result

- CloudHSM 실장비 검증 23케이스 중 21 통과 — PoC 목표였던 PKCS#11 연동 검증 달성
- 잘못된 키로 복원되는 경로가 구조적으로 차단됨 (지문 대조 + 주소 체계 + 기동 시 검증)
- 설계 문서·인수인계 문서를 코드와 함께 관리해 후임자가 흐름을 추적할 수 있는 상태로 유지

## Takeaways

보안 시스템에서 "동작한다"는 절반의 진실이다. 잘못된 입력이 **성공처럼 보이는 경로**를
찾아 막는 것이 나머지 절반이었다. 그리고 그 경로는 코드 리뷰가 아니라
"이 백업을 3년 뒤에 다른 사람이 복원한다면?"이라는 질문에서 나왔다.
